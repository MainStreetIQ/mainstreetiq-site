## Deploy & publish mechanics

- **Deploy is GitHub Pages, on push to `main`** (the `pages-build-deployment` Action). This repo is its OWN git repo (`MainStreetIQ/mainstreetiq-site`), separate from the parent `~/MSIQ` repo. It is NOT on Vercel — `vercel.json` (19 redirects) and `.vercelignore` are DEAD config, inert on Pages (adjudication pending, plan P5). Before asserting anything about deploy behavior, probe the live surface (`curl -sI` headers, a URL that should/shouldn't exist) — config-file presence is weak evidence and has already put a wrong platform claim into a committed doc.
- **A push that touches `.github/workflows/` needs `workflow` token scope, and no Claude session can grant it (learned 2026-08-03).** The rejection reads `refusing to allow an OAuth App to create or update workflow .github/workflows/scheduled-publish.yml without workflow scope`, which names the FILE and so reads like a repo or branch permission problem. It is not; it is a scope on the credential. **Do not retry the push, and do not try `gh auth setup-git`** (the helper is already `osxkeychain`; the helper is not the problem). **`gh auth refresh` cannot be run from a Claude session** either: it blocks on a TTY prompt that never arrives and dies at exit 144 when killed. Hand Scott exactly one line to paste in his own terminal, then keep working on anything that does not need the push: `gh auth refresh -h github.com -s workflow`. If only the workflow change is blocked and the rest must ship, keep the workflow edit as the TIP commit and push `HEAD~1:main`.
- **The three directory hubs must always be referenced WITH a trailing slash: `/blog/`, `/glossary/`, `/legal/`.** Pages 301s an extensionless directory path to its trailing-slash form, and those three are directories holding an `index.html` with **no sibling `.html`**. `/our-work` does NOT redirect because `our-work.html` exists alongside `our-work/` — that asymmetry is why the bug reads as inconsistent and is easy to dismiss. On 2026-08-09 GSC mailed a "Page with redirect" notice: `/blog` and `/glossary` were submitted bare in `sitemap.xml`, so Google excluded both hubs from the index, and each hub's `rel=canonical` pointed back at the bare redirecting URL. Apply the slash in **every** surface: `sitemap.xml` `<loc>`, `rel=canonical`, `href`, `llms.txt` / `llms-full.txt`, and the `SearchAction` urlTemplate in `index.html`. Fixed in `37ea1f1` (418 lines / 149 files).
  **Two producers hardcode `href="/blog"` in the footer template and will silently revert a site-wide fix on their next run — fix the artifact AND both of them: `_scripts/footer_sweep.py` and `_scripts/build_ai_visibility_pages.py`** (plus any `_scheduled/` drafts, which carry the footer too). Same producer-bug shape as the `sitemap.xml` scheduler gap above. Note that apex→www and http→https 301s are correct and deliberate; they will always appear in that GSC report and are never the defect.
- **Draft privacy gate = Jekyll's underscore-directory exclusion.** `_scheduled/` and `_scripts/` stay off the live site ONLY because of the leading underscore. **NEVER add `.nojekyll`** (the common asset-fix reflex) — it would instantly publish every staged draft.
- **Scheduled publish:** `.github/workflows/scheduled-publish.yml` runs `_scripts/publish_scheduled.py` daily and stages exactly `git add blog/ llms.txt sitemap.xml` — the three files the script is capable of writing, and nothing else, so a stray working-tree file can never be swept into prod. A post change that touches any OTHER file must be committed separately or it won't ship with the post.
  **AMENDED 2026-08-03. `sitemap.xml` was NOT staged before that date, and the script did not write it at all.** The consequence was silent and total: nothing in the repo ever added a sitemap entry for a drip-published post, so all 12 posts the Action had ever published were absent from `sitemap.xml` (35 of 47 live posts listed), including all six "Found by the Machine" AI-visibility posts. A backfill alone would have re-broken on the next drip. The fix was structural, in three parts, and all three are load-bearing: (1) the script now owns per-series `<!-- ATC-SITEMAP-* -->` / `<!-- AIV-SITEMAP-* -->` marker pairs in `sitemap.xml`, exactly as it already owned the `*-GRID-*` and `*-LLMS-*` pairs; (2) the Action stages `sitemap.xml`; (3) the 12 missing entries were regenerated by running the script, not hand-written. **Do not "simplify" the workflow's `git add` back to two paths.**
- **The scheduler diverges `main` between sessions — ALWAYS `git fetch origin main` + rebase before any manual push.** The daily Action commits `blog/*.html` + `blog/index.html` + `llms.txt` + `sitemap.xml` (~16:0x UTC), so a manual push staged against a stale local `main` will be rejected as non-fast-forward. The recurring collision files are `llms.txt` and, since 2026-08-03, `sitemap.xml` (the scheduler regenerates blocks in both). If you're holding stale local copies (e.g. a deferred ICP rewrite), `git stash push -- llms.txt sitemap.xml` to clean the tree, rebase onto `origin/main`, push, and do NOT pop the stash over the scheduler's fresh files. Your top-level page edits never collide with `blog/`, so the rebase is conflict-free once those two are out of the working tree. (2026-07-21: free-sweep push rejected this way; fetch+stash+rebase resolved it.)
  **Note the asymmetry on `sitemap.xml`:** only the marker-delimited blocks are scheduler-owned. Hand-maintained entries (every non-drip page) sit outside them and are safe to edit directly, so a conflict there is a real conflict, not a regeneration artifact.

## Blog drip system

- Posts stage in `_scheduled/<series>/` with a per-series `manifest.json`; the daily Action promotes each into `blog/` on its slot date and rebuilds three marker-delimited blocks per series: the card grid in `blog/index.html` (`ATC-GRID-*`, `AIV-GRID-*`), the block in `llms.txt` (`*-LLMS-*`), and the `<url>` entries in `sitemap.xml` (`*-SITEMAP-*`, added 2026-08-03). Multi-series via the `SERIES` registry in the script. A NEW series needs: registry entry + `_scheduled/<key>/manifest.json` + post HTML + **all three** marker pairs in `blog/index.html`, `llms.txt`, and `sitemap.xml` — a missing pair is a hard `SystemExit`, not a silent skip, which is deliberate. Edit a pre-date post in its `_scheduled/` source; picked up on its cron run. Dry-run: `python _scripts/publish_scheduled.py --check` or `--date YYYY-MM-DD`.
- **The scheduler is self-reconciling, so a gap in a scheduler-owned block is repaired by RUNNING it, never by hand-writing the missing entries.** That is how the 12 missing sitemap entries were backfilled on 2026-08-03: add the markers, teach the script, run it. Hand-writing them would have produced the same bytes and left the next drip broken. Verify with a second run — it must report `No changes (already in sync)`.
- **Editing a scheduler-OWNED `llms.txt` marker block (`ATC-LLMS-*`, `AIV-LLMS-*`) is non-durable in `llms.txt` — fix the SOURCE.** The block text is regenerated from each series' `manifest.json` `llms_desc` field on every Action run, so a hand-edit inside the markers is overwritten the next day. To change a block line permanently (e.g. strip an em-dash), edit the post's `llms_desc` in `_scheduled/<key>/manifest.json`; the `card_desc` field feeds the `blog/index.html` grid separately. Only content OUTSIDE the marker pairs (header/positioning blockquote, Core Services, Case Studies, RAID, Contact, Service Areas) is hand-maintained and safe to edit directly. To VERIFY a manifest fix matches what the scheduler will regenerate: `cp llms.txt <scratch>/mine`, run `_scripts/publish_scheduled.py`, `diff` just the block (`sed -n '/ATC-LLMS-START/,/ATC-LLMS-END/p'` on both), then restore with `cp <scratch>/mine llms.txt` — **NEVER `git checkout -- llms.txt` while your own uncommitted edits live in that file; it silently clobbers them** (learned 2026-07-23, the deferred ICP rewrite). The scheduler run also dirties `blog/`; revert those with `git restore blog/` + `rm` any stray promoted post, since promotion is the Action's job, not a manual push's.
- Blog posts drafted via the blog-draft skill must NOT include a `## TL;DR` heading in `body_md` — render.py builds the styled aside from the separate `tldr` field; a body TL;DR renders twice.

## Verification harness

- Browser-verify style work before commit with `~/MSIQ/.venv/bin/python` + Playwright headless Chromium on `file://` URLs; screenshot to scratchpad and Read the PNG; catch JS errors via `page.on('pageerror')`. Desktop 1440x900 + mobile 390x844 covers both breakpoints.
- **Subdirectory pages (e.g. `/glossary/*.html`) use ABSOLUTE asset paths (`/styles.css`, `/assets/...`) and render UNSTYLED over `file://`** (the leading `/` resolves to the filesystem root, not the repo). Verify those over a local HTTP server instead: `python3 -m http.server 8899 --directory .` then load `http://localhost:8899/<page>.html`. Note python's http.server has NO extensionless-URL resolution (hit `.html` locally), but GitHub Pages does (production links stay extensionless). Root-level pages use relative paths and still style over `file://`.
- **`:focus-visible` must be verified with a real keyboard Tab** (`page.keyboard.press('Tab')` loop until `document.activeElement` is the target). Programmatic `element.focus()` + getComputedStyle false-negatives (outline reads back as currentColor).

- **Bust the CDN cache before calling a deploy wrong (2026-08-03).** A plain `curl` of a
  just-pushed asset measures the CDN edge, not the deploy. Also note `mainstreetiq.com` 301s to
  `www.`, so a `curl` without `-L` measures a redirect stub and its md5 is meaningless. Verify with
  `curl -sL "<url>?cb=$(git rev-parse --short HEAD)"` plus
  `gh api repos/MainStreetIQ/mainstreetiq-site/actions/runs` to confirm the build ran. Only call a
  deploy wrong when a cache-busted fetch of a successfully-built commit still mismatches.
